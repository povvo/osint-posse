# Database Usage Guide

**ospo-db** is the recommended persistent investigation database: an
authenticated Cloudflare Workers MCP service backed by D1. It is the database
for investigations, entities, relationships, grades, timelines, evidence,
locations, notebooks, and cross-session workflow progress.

---

## Data Model

All data is scoped to an `investigation_id` obtained from
`ospo-db:create_investigation`. The Worker validates bounded enumerations and
relationship endpoints, while the local task runner remains responsible for
workflow-state validation.

### POLE Entities

Persons, organisations, locations, events, objects, and other entity types identified during investigations. Each entity carries:

- `name` — primary name or title
- `type` — person, organisation, location, event, object, domain, email, phone, account, document, vehicle, address
- `aliases` — alternative names, trading names, maiden names
- `identifiers` — passport, company number, LEI, DUNS, tax ID, custom
- `attributes` — birth date, nationality, jurisdiction, status, etc.
- `source` — provenance of this record
- `source_grade` — Admiralty 6x6 grade (e.g. A1)
- `notes` — free-text analyst notes

**Tools:** `add_entity`, `search_entities` (query + type filter), `update_entity`

### Relationships

Directed and undirected links between entities. Each relationship carries: source and target entity IDs, type (e.g. `director_of`, `shareholder_of`, `communicated_with`), direction, confidence weight, source grade, and notes.

**Tools:** `add_relationship`, `get_relationships` (by entity ID)

### Timeline Events

Chronological records with datetime, description, category (communication, movement, financial, meeting, incident, document, other), involved entities, location, and source.

**Tools:** `add_timeline_event`, `get_timeline` (filterable by category and entity)

### Geo-Intelligence

Point locations associated with entities. Each location carries a label, coordinates, entity reference, observation timestamp, source, and source grade.

**Tools:** `add_location`

### Evidence Metadata

Registry of preserved evidence artefacts. Each entry carries a description, artefact type, SHA-256 hash, URL, and storage location.

**Tools:** `register_evidence`

### Source Grades

Admiralty 6x6 grades recorded per claim. Each grade carries the source name, reliability (A-F), credibility (1-6), the claim text, and justification.

**Tools:** `record_grade`

### Investigation Notebook

Free-form markdown content persisted directly — no script intermediary. Captures analytical position, unresolved questions, and decisions.

**Tools:** `save_notebook`, `load_notebook`

### Task Progress

Task runner state: current task index, completed task IDs, and verified
completion records.

**Tools:** `save_progress`, `load_progress`

---

## Maintenance Rules

1. **Every entity must have a source and source grade.** No record enters the database without Admiralty 6x6 grading.
2. **IDs are generated by ospo-db.** Do not fabricate entity IDs — use the ID returned by `add_entity`.
3. **Write as you go.** Entities, relationships, evidence, grades, and locations are written to ospo-db as they are produced — do not batch to session end.
4. **Notebook and progress are checkpointed.** Save progress after every `done` command. Save the notebook at phase transitions and whenever a finding materially shifts the picture.

---

## Session Protocol

### Session start

1. Call `ospo-db:list_investigations` to identify the active case
2. Call `ospo-db:load_progress` with the `investigation_id` to restore task runner state
3. Call `ospo-db:load_notebook` to restore the Investigation Notebook
4. Resume from the current task position

### Session end

No special action required if write-through discipline was maintained. If in doubt, call `ospo-db:save_progress` and `ospo-db:save_notebook` as a final checkpoint.

## Investigation Lifecycle

### Starting a case

Call `ospo-db:create_investigation` with a descriptive case name. The returned `investigation_id` scopes all subsequent calls.

### During a case

Use `ospo-db:get_statistics` for a dashboard view of entity counts, relationship counts, timeline events, evidence items, and grades.

Use `ospo-db:load_investigation` for a full state dump — useful for feeding `network_graph.py` or `chronological_matrix.py` with complete data.

### Closing a case

1. Verify all 56 tasks complete via `task_runner.py status`
2. Call `ospo-db:get_statistics` and record counts in the Case Summary Record
3. Call `ospo-db:close_investigation` to mark the case as closed
4. Closed investigations remain queryable via `ospo-db:load_investigation` for future cross-case reference

### Multiple investigations

ospo-db supports multiple concurrent investigations. Each maintains fully isolated entities, relationships, timeline, evidence, grades, notebook, and progress. Use `ospo-db:list_investigations` to see all cases.

---

## Known Limitations

- Delete operations exist, are authenticated, and still require explicit user
  confirmation under the skill decision protocol. Prefer closure or archival
  when an audit trail matters.
- There is no cross-investigation query tool. Cross-case analysis requires
  separately loading authorised investigations.
- The bearer credential grants the configured client the Worker tool surface;
  deploy behind Cloudflare Access when per-user identity or role separation is
  required.
